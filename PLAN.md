# fpLog — plan

**Goal. Record a log-encoded picture on the SIGMA fp that takes a fraction of the
storage the camera's raw modes need**, from the SD card, **in RAM only**, and grade
it in DaVinci Resolve.

**Storage reduction is the objective.** Where space and picture quality conflict,
space wins — that is what makes this project different from `fpLossless` and from
OpenGate, and it decides the container.

**First target: FHD 24p. Nothing else until that works end to end.**

**Status, 2026-09-22 — IT RECORDS LOG.** Colour mode Off carries a bit-exact
ARRI Log C V3 EI 800 curve, verified by reading the table back off the camera
([`results/log2/`](results/log2/FINDINGS.md)). §10 stage D is done and
[`share/`](share/) is the distributable card.

**What that does not mean.** §7 is entirely unverified and the exposure series is
unshot, so the dynamic range this carries is **not measured** — and neither is
§7.1, storage, which is the objective the whole project is justified by.

**Status, 2026-09-22 — the kill criterion is ANSWERED YES.** The container is
decided and measured (§1). The DRAM dump exists. **The RGB transfer function is
found, writable from a card, and reaches the recorded file**: inverting curve #82
of the 452-curve registry and toggling the colour mode turned the picture
negative in live view *and* in the MOV ([`results/invert/`](results/invert/FINDINGS.md)).

**What is left is no longer a search.** Three things stand between here and a
release: a **switch** (the curve is global, so §4B is dead and nothing replaces
it yet), the **stage characterisation** the curve must be fitted to (§10 stage B),
and the **curve itself** (§10 stage C).

**→ [`docs/CURVE_TARGETS.md`](docs/CURVE_TARGETS.md) is the live plan: where a
log curve should sit, ranked. [`docs/ISP_PIPELINE.md`](docs/ISP_PIPELINE.md) is
the reference it rests on — the ISP stage map, the eight ISP patterns, and how
the MOV and CinemaDNG paths differ.** This page stays as the project's
reasoning: container, curve design, safety and verification.

## 1. The container, decided by the numbers

FHD 24p, 1936×1090 stored:

| | MB/s | GB/min | vs stock 12-bit |
|---|---|---|---|
| CinemaDNG 12-bit (stock) | 75.9 | 4.55 | 1.0× |
| CinemaDNG 10-bit (stock) | 63.2 | 3.79 | 1.2× |
| CinemaDNG 8-bit (stock) | 50.6 | 3.04 | 1.5× |
| CinemaDNG 12-bit + lossless JPEG ~2:1 | 37.9 | 2.28 | 2.0× |
| CinemaDNG 10-bit log + lossless | ~39 | ~2.4 | ~1.9× |
| **MOV H.264 — MEASURED** | **9.9** | **0.593** | **7.7×** |

*(The MOV row is measured from a real clip — `results/mov_recording/FINDINGS.md`.
77.0 Mbps video, 79.0 Mbps for the file. The first draft of this table guessed
100–200 Mbps and tabled 6.1× at best; the truth is better.)*

**The entire raw family caps out at about 2×.** Bit depth, log companding and
lossless compression all attack the same redundancy, and none of them — nor all of
them together — gets past roughly half of stock. A 10-bit log CinemaDNG saves 17%.
That is not the goal as stated.

Only a lossy codec reaches "a lot", and **the fp writes exactly two containers
without a new muxer: CinemaDNG and MOV.** CinemaDNG is excluded by the objective.

**So the container is MOV, and the codec is the camera's own H.264** — which is
also what the original brief asked for. The earlier draft moved away from it on
quality grounds; that concern was real but it is subordinate to the actual goal,
and the intervening 10-bit DNG detour bought 17% where the objective needs 6×.

### What this costs, stated plainly

**Measured, not assumed:** the MOV is **8-bit 4:2:0 H.264, High profile, level
5.1**. Log in 8-bit lifts the shadows and then asks a lossy 4:2:0 encoder to carry
the lift. Expect banding in skies and smooth gradients, and chroma noise that
grades worse than a raw file would.

**Three measured facts soften it**, none of which was assumed:

- **Full range** (`yuvj420p`, `color_range=pc`) — 256 code values per channel, not
  219. **1.17× more levels, and §2's curve must be fitted to 0–255.**
- **ALL-I** — 48 of 48 frames are I-frames. Lifted shadow noise cannot propagate
  through inter-frame prediction. The best thing about this container for log.
- **VBR, not capped CBR** — an 8.95× frame-size spread, so log content can take
  the bits it needs.

This is a real cost and the README must lead with it. It is also what every 8-bit
log camera has shipped with, and people have shipped work on it. **The mitigations
are in §2 and they are not cosmetic** — a curve fitted to this sensor is worth
several stops' worth of code values over a spec-exact one.

### If 8-bit proves too fragile

The camera shoots JPEG stills, so a **lossy** JPEG encoder exists in silicon —
distinct from the lossless engine at `0x300D0000` that `raw-sup.md` measures.
Motion JPEG is intra-only, 8- or 12-bit, Resolve reads it, and it would sit
between H.264 and raw on both axes.

It needs a muxer written and running on-camera, which is a second project. **Not
the plan. The documented fallback if §7 fails**, and a reason to find out during
Phase 1c whether that encoder is reachable during video.

## 2. The curve — and a reversal

The previous draft recommended a **spec-exact** DaVinci Intermediate curve, because
under the DNG plan the curve was self-describing and exactness bought a free,
LUT-less decode. **That advantage died with the DNG container, and in 8-bit the
reasoning inverts.**

DaVinci Intermediate spans roughly 16.5 stops. The fp delivers perhaps 12. Encoding
a 12-stop sensor through a 16.5-stop curve spends about a quarter of the code values
on range the camera cannot produce — **in 8-bit that is around 70 of 256 codes
thrown away**, and those codes are exactly what is standing between the picture and
visible banding.

**Recommendation: a reduced-range log fitted to the fp's measured dynamic range.**
Same shape as DaVinci Intermediate — a linear toe into a log segment — with the
constants solved so the curve's black and white land on the sensor's actual black
and clip.

The cost is that Resolve no longer has a matching dropdown, so **fpLog must ship its
own decode**: a `.cube` and a DCTL, generated by the same tool that generates the
camera-side table so the two cannot drift. `fp_sup/projects/color-sup.md` has walked
into DCTL delivery before and found it awkward — read that page before designing
the deliverable, because "reproducing a colour and shipping a colour tool are not
the same job" is the lesson it paid for.

**Decide by measurement, not preference.** Phase 2 scores candidate curves as
quantisation error against modelled sensor noise, per level, at 8-bit, with
spec-exact DaVinci Intermediate as the reference to beat. If the fitted curve does
not beat it by enough to justify shipping a DCTL, ship the spec-exact one and take
the dropdown.

## 3. The kill criterion

**Is there a programmable LUMA tone curve in the ISP path that feeds the H.264
encoder, or a parameter block that reaches it?**

If neither exists, stop and write down what was ruled out.

> **Status: ANSWERED YES, 2026-09-22.** Curves #82 and #16 of the 452-curve
> registry were inverted in DRAM and the colour mode toggled to force the
> upload. **The picture went negative in live view AND in the recorded MOV** —
> the first write in this project to reach a recorded file.
> [`results/invert/FINDINGS.md`](results/invert/FINDINGS.md).
>
> The curve is **global, not per colour mode**: other modes inverted too, though
> only #82 and #16 were written. That confirms `docs/MAIN_GAMMA.md`'s negative
> result from the other side — colour mode never moved this stage — and it
> **breaks §4B**, because the switch can no longer be a colour mode.

A CPU pass is not the fallback. FHD 24p is 2.11 Mpx/frame, 50.6 Mpx/s, and the
picture at that point is YUV 4:2:0 — the *hardware* lossless-JPEG engine measures
169.7 Mpx/s, and a CPU loop will not be within a small factor of that. **Do not
build it.**

### The question that could change everything

**Does the H.264 encoder block support High10 or 4:2:2, and is it reachable?**

Hardware encoders of this class frequently support profiles the firmware never
exposes. 10-bit log H.264 would remove most of §1's cost at no storage penalty
worth naming. It is a long shot and it is cheap to check once the dump exists —
**check it early in Phase 1c, before committing to an 8-bit curve design.**

## 4. Architecture

### What carries over from Phase 1, and what does not

`docs/PIPELINE.md` was written against the **CinemaDNG geometry path**. The
infrastructure transfers; the target does not.

**Transfers:**

- The **VBIN payload mechanism** and the card build recipe.
- The **detour idiom** — latch the decision in payload state, branch on the return
  address when one routine serves several callers, tail-jump to the instruction
  after the patched one, keep a counter and the last-seen argument in a fixed
  scratch word so a failure can be read out afterwards.
- The **32 mode-independent `1600` writes** at `0xC0BD9A2C…` / `0xC0BE167C…`, which
  both OpenGate builds make identically. Probably needed; copy them, and find out
  what they are before shipping.
- The lesson that **geometry was written in three separate copies**, and that OG3K
  v0.2.2a shipped broken because one was missed with no sign on screen. **Whatever
  fpLog writes, find every copy of it.**

**Does not transfer:** the `0xC043xxxx` cluster and the descriptor at
`context + 0x5C` were mapped as the *recording format* path. Whether that descriptor
also serves the MOV pipeline is an open question the dump answers — do not assume it.

### The two candidate mechanisms

**A. Re-program the ISP's output tone curve.** If it is a table in RAM this is free
at runtime, frame-rate independent, and a single `mem set` sweep. First thing to
look for.

**B. Take over a colour-mode slot.** Point a non-Standard colour mode at our own
parameters. The UI, persistence and plumbing already exist. OpenGate does exactly
this with the third resolution entry, and `resources/fp_sup/docs/MENU_MODIFICATION.md` shows every
menu item carrying its metadata in ROM right after its name string.

**A if Phase 1c finds the table, B otherwise.** They are not exclusive — B is the
likely UI even when A is the mechanism.

> **B is dead, 2026-09-22.** `results/invert/` proved the transfer function is
> **shared across colour modes** — inverting Off's and Teal & Orange's curves
> inverted the picture in *other* modes too. So pointing a colour-mode slot at
> our own curve does not give a per-mode switch; it gives log everywhere.
> **A is the mechanism and B is not the UI.**
>
> **This does not block shipping. The card is the switch** — card in, log; card
> out and battery cycled, stock, which is how every fp_sup product ships and
> needs no menu work at all. What is lost is toggling log without a power cycle.
> Two costs go in the README instead: **shoot in mode Off**, because every other
> mode applies its styling to a log signal; and the upload fires on mode
> selection, so §8 question 10 has to be settled first.

## 5. Phases

### Phase 0 — done

`docs/FIRMWARE_BASE.md`. Image pinned at
`c9fa76f32f523bb2dc9a3fbda39418c31573cab6a1aa5c56d28c371862066ed8`; **the update
file is packed and cannot be disassembled.**

### Phase 1a — the dump *(the gate on everything)*

```bash
python3 camera/build_dump_card.py --out camera/dump_card
```

`AutoRun.txt` alone on a cleared card. **`mem save` only** — no `mem set`,
nothing non-volatile, no payload. Then `tools/reassemble_dump.py`.

**Default range `0xC0000000..0xC4000000`, not just the firmware image.** The
image ends at `0xC2F30800`, but **39 of the addresses in `ADDRESSES.md` sit
above it**, up to `0xC38D2DE8` — live state, heap, object pools. If the *active*
tone curve is a RAM copy rather than the ROM default, that is where it lives,
and a dump stopping at the image would miss it. The image is written first, so
a stop above it still leaves the part that matters.

### Phase 1b — measure a stock clip *(no dump, no patching — do it first)*

Shoot one stock FHD 24p MOV and run `ffprobe`/`mediainfo` over it. This is the
cheapest step in the project and it prices the whole thing:

- **bit depth and chroma subsampling** — the §1 assumption, confirmed or destroyed
- **actual bitrate**, so §1's table stops being a range
- whether bitrate is user-selectable, and whether ALL-I exists
- what the `colr` atom declares, and what Resolve does with it
- GOP structure — inter-frame prediction on log shadows is where banding is born

### Phase 1c — find the curve

Against the dump:

1. **Does the H.264 block do High10 / 4:2:2?** (§3) — before anything else, because
   a yes rewrites §2. **Run 1 could not answer this**: the encoder probe completed
   cleanly but every codec block read dead, because they are clock-gated when idle
   and an AutoRun runs at boot. See `results/run1_21_09_2026/FINDINGS.md`; the fix
   is step 2 of §9.
2. Map `movrec` (`0xC0403558`) from the command table at `0xC0BAC14C` to the
   encoder's input.
3. Map `pic` / `optic` (`0xC0404E98`, sub-table `0xC0BC00E8`). These already expose
   per-ISP-function `0 auto / 1 force_off / 2 test` over distortion, aberration,
   shading, 3ddnr, monofilter and tbsd — so ISP feature blocks are individually
   addressable. Find out whether a tone block sits in the same structure.
4. Find the colour-mode parameter block: Standard, Vivid, Teal & Orange have to
   differ somewhere, and that difference is the shape of what we need to write.
5. Is the lossy JPEG encoder reachable during video? (§1 fallback.)

**Out:** `docs/PIPELINE.md` extended with a named write target, or a documented stop.

### Phase 2 — the curve, offline

`tools/curve/` generates, from one source of truth: the camera-side table, the
`.cube`, and the DCTL. Tests for monotonicity after 8-bit quantisation, exact
endpoints, and round-trip error.

Then the bake-off in §2, scored against a noise model, on real fp footage.

### Phase 3 — camera-side payload

Follow `fp_sup/.claude/skills/fp-usb-shell/SKILL.md`; its constraints were paid for.

- **Borrow a shell command handler** (`echo`, entry 17, pointer at `0xC0BAC2F8`) for
  one-shot work. Not the gyro callback — it may not block or take a mutex.
- Resident work goes on the firmware's **thread pool** (`XT_CREATE 0xC036E108`,
  `XT_ATTACH 0xC036E1B8`, `XT_JOIN 0xC036E1F8`, `XT_DESTROY 0xC036E168`), passing
  the **address** of the vtable word, not its contents.
- **`stksz` never above `0x2000`** — the pool is shared; raising it has corrupted
  other tasks.
- Never the `Cyc` pair (`0xC01F885C` / `0xC01F8D90`); it freezes the camera.
- **Call the routine directly once before hooking it to anything.**

**Out:** `camera/payload.S`, `camera/build_card.py` → `AutoRun.txt` + payload.

### Phase 4 — the switch and the monitoring decision

A colour-mode slot per §4B, named so it reads as log.

**Decide explicitly and write the answer down: does the LCD go flat too?**
Recording log while monitoring Rec.709 needs two render paths and may not be
reachable. If it is not, flat monitoring is the cost and the README says so before
someone loses a take to it.

### Phase 5 — verification (§7). Phase 6 — release.

Only after FHD 24p passes: other frame rates, then UHD.

## 6. Safety

1. **Volatile only.** `mem set` and a RAM payload. No `prom write`, no `fwup`, no NAND.
2. **Ver.5.02 only.** Refuse to build if the pinned hash does not match; put the
   version in the on-screen banner so a result can be attributed to a build.
3. **Revert:** delete `AutoRun.txt`, **battery out** — a warm restart does not clear
   RAM — power on, confirm stock.
4. **One variable at a time.** Mixed variables have already produced wrong
   conclusions on this camera.
5. **Judge from a clean boot.**
6. **After a freeze, read the card first** — whatever the hook wrote is still there.
7. **Do not cold-call the lossless-JPEG engine at `0x300D0000`.** It broke stills
   compression until a reboot. Hook it, do not call it.
8. Never touch `0xC343A624.2` (`still_raw_dump`) — it hangs the camera.

## 7. Verification

Storage is the objective, so it is measured first and it is the headline number.

1. **Space.** GB/min for one scene, stock MOV against fpLog MOV against stock
   CinemaDNG 12-bit. **The claim is a multiple against raw; state it as a measured
   multiple or do not state it.**
2. **Curve accuracy.** Grey step wedge, same scene and exposure as a CinemaDNG
   reference. Decode the MOV with the shipped inverse and compare linear values per
   patch. State the error at both ends rather than quoting only the mid-range.
3. **Banding — the thing most likely to sink this.** Smooth gradient at base ISO:
   distinct code values across it for stock MOV and fpLog MOV, plus a visual check
   after a 2-stop lift. Compare against Phase 2's prediction — *if the prediction was
   wrong the model is wrong, and that matters more than the measurement.*
4. **Grade headroom.** ±2 stops exposure and a white-balance shift, looking for
   posterisation and chroma break-up. A log file that cannot take a grade has no
   reason to exist.
5. **Clipping.** Nothing clips that did not clip before, at either end.
6. **Neutrality.** Grey stays grey through the curve; per-channel error means the
   write hit a matrix, not a curve.
7. **Recording integrity.** Duration, frame rate, audio sync, file size, in-camera
   playback, against a stock clip. fpLog is a picture change; if it changed the
   recorder, it is a bug.
8. **Revert.** Card out, cold boot, shoot, confirm stock.
9. **Every ISO**, as OG3K did — base plus both extremes, at FHD 24p. State exactly
   what was tested and do not generalise.

### The three that decide the project

**Step 3 — the dump.** `camera/build_dump_card.py`, read-only. Nothing
is written to NAND, EEPROM or anything else non-volatile. Until it exists, every
firmware question is unanswerable: the update file is packed
(`docs/FIRMWARE_BASE.md`), and a byte search over it returns pure noise —
`6e 00 33` (High 10) occurs exactly as often as `64 00 33`, the profile actually
in use, nine times each.

**Step 5 — the WRITE MECHANISM passed; the curve did not.** Overwriting the
DRAM source at `0xC0B3B2E8` changes the rendered picture, confirmed through the
source, the ISP registers and the image together
([`results/looksrc1/FINDINGS.md`](results/looksrc1/FINDINGS.md)). That is the
asset. But the stage it moves is **chroma**: contrast never changed in any mode
across four runs, and Monochrome never changed at all
([`results/logoff1/REFRAME.md`](results/logoff1/REFRAME.md)).

**Two claims made here have been withdrawn.** That the 89-curve bank is the tone
curve — it is inert, repointed live with no effect
([`results/selector/`](results/selector/FINDINGS.md)). And that overwriting one
of those 89 tables would be the product — nothing reads them.

**What the mechanism is worth anyway:** *do not move the data, change what the
firmware moves.* Five verified writes have now failed to reach the picture and
one has succeeded, and the one that succeeded was the only one aimed at an
address found by searching the dump for the values the hardware was actually
holding. Apply the same method to the RGB transfer function —
`docs/CURVE_TARGETS.md`.

**Step 9 — the decisive experiment.** Write the curve table by hand, camera idle,
over `shl mem set`, and look at the picture. **No payload needs to exist for
this.** If the image changes, the mechanism is proven and steps 10–11 are
packaging. If it does not, the target was misidentified and it is back to step 5.
Nothing else in this list carries that much information for that little work.

### On 10-bit, honestly

`tools/find_encoder_cfg.py` makes step 4 one command, and it is self-tested: a
synthetic positive control (including a deliberately misaligned decoy that must
not match) and 32 KB of real shipped ARM as a negative control, where it produces
no false cluster.

**That makes the check cheap. It does not make the answer likely.** The prior
remains that this is an 8-bit path end to end — an 8-bit ISP output feeding an
8-bit encoder is the ordinary arrangement — and profile 100 in the SPS is a
label, not a capability (`results/mov_recording/FINDINGS.md` §4). The reason to
run it is that it costs one command, and a yes would change §2 completely.

**Plan for 8-bit.** Treat 10-bit as an upside to check, not a branch to design
around.

## 10. Implementing log footage — the detailed plan

**Everything here is behind §9 step 5.** If no programmable tone curve and no
reachable colour-mode block exists, this section does not happen; write down what
was ruled out instead (§3).

Written for **FHD 24p only**. Every step says what it produces and what would
make it stop.

### Stage A — locate the write target *(§9 step 5, expanded)*

**Superseded in detail by [`docs/CURVE_TARGETS.md`](docs/CURVE_TARGETS.md)**,

established. Recorded here is only what each sub-step turned into:

| | |
|---|---|
| **A1** | Walk `movrec` (`0xC0403558`) to the encoder's input. **Partly done, from the dump rather than the disassembler** — the module map, the ISP stage order and the MOV/CinemaDNG split are in `docs/ISP_PIPELINE.md`. The register bases are still unknown. |
| **A2** | Walk `pic` (`0xC0404E98`) and its sub-table (`0xC0BC00E8`). **Done, and answered no** — the firmware printed its own `pic` usage to the card and there is no tone or gamma entry (`results/shellcap/`). |

### Stage B — characterise the sensor, offline

| **B1** | Measure the real dynamic range: noise floor to clip, in stops, per ISO. §2 fits the curve to *this*, not to a spec's 16.5 stops. |
| **B2** | Build the noise model — read noise and shot noise per level — that the bake-off scores against. |
| **B3** | Measure where the stock picture already clips, so the log curve can be checked against not making it worse. |

**Produces:** `docs/SENSOR.md`, with the numbers the curve is fitted to.
**Stops if:** the measured DR is close to 16.5 stops, in which case the fitted
curve buys nothing and §2 reverts to spec-exact DaVinci Intermediate — which
would be good news, because Resolve then needs no DCTL.

### Stage C — the curve, offline

| | |
|---|---|
| **C1** | `tools/curve/` — one generator, three outputs from one source of truth: the camera-side table, a `.cube`, and a DCTL. They cannot drift because they cannot be produced separately. |
| **C2** | Tests: monotonic **after** quantisation to the hardware's element width, endpoints exact, round-trip error bounded, and the table's length and packing exactly what stage A measured. |
| **C3** | The bake-off — fitted curve against spec-exact DaVinci Intermediate, scored as quantisation error versus modelled noise per level, at 8-bit, on the real frames from stage B. |
| **C4** | Predict the banding. A number, before any camera time. |

**Produces:** the generator, its tests, the chosen curve with the measurement that
chose it, and a banding prediction to check §7.3 against.

### Stage D — the payload

Follow `fp_sup/.claude/skills/fp-usb-shell/SKILL.md`. The constraints in §5
Phase 3 are not optional and they were each paid for.

| | |
|---|---|
| **D1** | Write the table with the camera idle, by hand, over `shl mem set`. Look at the picture. **This is the whole experiment, before any payload exists** — if a hand-written table changes the image, the mechanism is proven and everything after is packaging. |
| **D2** | Same write from a borrowed command handler (`echo`, pointer at `0xC0BAC2F8`). Call it directly once before hooking it to anything. |
| **D3** | Make it survive a mode change and a record start/stop — find every copy of the target, the way OG3K v0.2.2a did not. |
| **D4** | `camera/payload.S` + `camera/build_card.py`, with an overlap check against the generated AutoRun like `build_probe_card.py` has. |

**Produces:** a card that records log.
**Stops if:** D1 changes nothing. Then the target was misidentified — back to A.

### Stage F — verification and release

§7 in full, and **§7.1 first**: storage is the objective, so the headline number
is GB/min measured against stock CinemaDNG, stated as a measured multiple or not
stated at all.

Then §7.3 banding against stage C4's prediction — *if the prediction was wrong,
the model is wrong, and that matters more than the measurement.*

Release per §5 Phase 6: what was verified **and what was not**, in the style of
`fp_sup/releases/*/README.txt`, with the DCTL and the Resolve recipe in the same
archive.

### What would make the whole thing stop

1. **No programmable curve and no reachable colour-mode block** (stage A). The
   kill criterion. A CPU pass is not the fallback — §3.
2. **The measured DR makes the fitted curve pointless** (B3). Not fatal; §2
   reverts to spec-exact and the project gets simpler.
3. **8-bit log will not take a grade** (§7.4). Then MJPEG via the stills JPEG
   encoder is the documented fallback (§1), and it is a second project — a muxer
   written and running on-camera.
