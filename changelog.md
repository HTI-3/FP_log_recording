*The error.* `docs/LOOK_CURVE.md` put the record id at `+0x030` and the second
knot array at `+0x092`; `docs/cards/blockb.md` said `+0x094`, and that
disagreement was never chased. The real layout is **knots A `+0x000`, gains A

gains B `+0x0C4`, slopes B `+0x0F4`**, stride `0x124`. It is pinned by a test:

→ `tools/look_records.py`, with a self-test that requires the old alignment to
be rejected.

*What it means.* Every record address in the repository is a **`knots B`**
address, `0x90` past the record it belongs to. `0xC0B3B2E8` is `knots B` of the
record at `0xC0B3B258`, id 11. No hardware result changes — the cards wrote the
array they meant to — but the labels invert: what was called "block A" is
`knots B` (writing it skews green) and what was called "block B" is `knots A` of
the *next* record (magenta).

*What else the dump then said.* **`knots A` is identity in all 36 records**, so
it has never carried anything. **`gains A` is shaped in 22 of 36 records and has
never been written** — nor have `slopes A`, `gains B` or `slopes B`. Two thirds
of every record is untouched. A scan of all 64 MB finds **exactly one bank** of
these records, so the luma curve is not in a second one. And the bank has an
outlier: a record at `0xC0B392B0` whose gains, slopes and `knots B` match no
template, with **three byte-identical copies in live RAM above the firmware
image** — composed at runtime, never written, never looked at.

*The observation the plan turns on.* Every search so far used the **colour

sweeps of `0x3020`–`0x3026` are therefore not negatives for luma; they are
untested. A luma-only variable has never been swept once.

**"11-bit index" withdrawn.** Request: why is the ISP tone map's input 11-bit
when no recording mode is?
It is not. The claim was inferred from `log2(2048)` alone. The same reasoning on
the LUTs actually seen in hardware gives 4.6 bits (24-knot look records) and 6.0
bits (the 65-knot ramp at `0x30210594`) — they are **knot counts**, not input
widths. `GAM_TOP` is named `GAMINT` / `GAM_BAS` / `GAM_GS GAMDEC` — base,
interpolate, decimate — which is a segmented gamma whose table holds knots and
serves an input of any width. And the data only half fits: 12 of the 89 curves
run `0..2047 → 0..8191`, but 77 top out at **8190** and saturate at index
1918–1919, exactly `15/16` of the range, which no bit width explains. 2048 is
also just the bank's stride, `0x1000` bytes ÷ 2, with no padding between tables.
None of it was load-bearing anyway: the bank is inert.
→ `docs/BIT_DEPTH.md` row struck out and a section *A table length is not an
input width* added.

**Why invert.** The earlier design flattened a few hundred entries, which shows
up as a band on a gradient — and whether a band is there is a judgement call on
a live LCD. This project has already drawn a wrong conclusion from "the picture
changed" once; the literal report of that run was *"it changed the color"* and
it took three more runs to correct (`results/logoff1/REFRAME.md`). An inverted
curve renders a photographic **negative**. Nobody has to decide whether they saw
it, and no confirming second run is needed.

**`v := max(table) − v`, and the maximum is measured, not assumed.** The payload
makes two passes: pass 1 takes each table's own maximum, pass 2 mirrors about
it. A hardcoded ceiling that was too low would clip instead of inverting, and a
clipped picture is exactly the ambiguous result this card exists to avoid. Each
output spans the same value range as its input and is monotonically decreasing.

**Both curves, #82 (Off) and #16 (Teal & Orange).** Off is the neutral mode and
the one to ship on, but every write this project has aimed at Off has failed to
move the picture, while the one write that *worked* was aimed at Teal & Orange
(`results/looksrc1/`, record id 11). Inverting both costs nothing, because the
mode toggle that forces the upload runs between exactly those two modes — so
both ends of the toggle land on an inverted table. If only one responds, that
asymmetry is the finding, and `check_invert.py` says so explicitly.

**Three rounds, four windows, twelve files.** Baseline / after the inversion /
after the toggle, over both tables, the live selector and the ISP shadow bank —
so "the write did not land", "the firmware rewrote it" and "it was never
uploaded" stay distinguishable instead of collapsing into one negative. The two
DRAM windows are read first, so there is always evidence on the card even if the
register read stops the payload — the lesson `isp_live_probe.S` v1 paid for.

**What the checker does NOT claim.** `0x30210594` was measured by
`results/isprobe_1/` as 65 × u16, `0 → 2048` in steps of 32 — a *unity* ramp,
which reads as a knot axis rather than as output values. So the tool does not
predict what it should become; it diffs the whole bank across the rounds and
prints that word's neighbourhood. Claiming to know what value to expect there
would be inventing a control.

payload's `adr`-relative `targets` and `windows` tables were verified by

**The halo is a cliff at the top of the table.** The spec-exact table's top

the frame and carries mean channel spread **69.6** against **6.6** everywhere
else — the colour lives entirely in it.

**The stock curve avoids it structurally**: sRGB reaches full scale at index
1918 and holds flat to 2047, so its ceiling *is* full scale. **A table's top
entry must be full scale**, and that flat top is a requirement of the stage
rather than decoration. `logc.py`'s self-test now asserts the property in both
directions and the builder warns whenever a table's top is short.
